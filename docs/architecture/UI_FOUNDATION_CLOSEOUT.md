This is the single checklist for the requests in this chat: review `feat/ui-foundation` against local `main`, finish the architecture work already started, preserve the current branch appearance, investigate sparse candidate reviews, search for similar mistakes, and identify backend behavior differences for a later intent-versus-drift discussion. A passing type check or shorter file alone is not merge approval.

## Confirmed findings and fixes

| Finding | Why it matters | Resolution and evidence |
| --- | --- | --- |
| Already-revealed platform interests lost the work profile after a reload. | `mapShiftInterest` exposes `userDetail`, while the Interested handler checked `user_detail`. The name and bio could survive while role, verification, location and skills disappeared. | Read the mapped field first and keep reveal caches consistent. Student and pharmacist tests cover both initial reveal and a previously revealed list response, including profile fields and no extra reveal request. |
| Candidate reviews could race each other. | An earlier slow ratings request could reopen the first candidate after the manager selected another candidate, and could replace the second candidate's ratings. | Guard review completion and ratings state by request generation; invalidate on reset, close and unmount. A delayed-response browser test verifies the latest selection and ratings remain. |
| Failed reveals could open an empty candidate review. | The reveal hook reports an error and returns `null`; three review handlers previously continued building a candidate anyway. | Stop on a failed reveal or superseded selection. The student reveal test injects a 500, verifies no dialog/private biography appears, then retries successfully with the same established endpoint/body. |
| Payroll switches lost their accessible name. | The installed MUI Switch constructs the input through `slotProps`; its internal slot replaced the deprecated `inputProps` label. | Use `slotProps.input` for `aria-labelledby`. The switch still waits for a successful PATCH and sends `{ pharmacy_id, use_chemisttasker_payroll }`. |
| Invoice links were not handled reliably while the workspace remained mounted. | Navigation could update the URL without opening the requested composer/review or could lose a request during a failed load. | URL-owned invoice state and generation guards; six earlier behavior tests retained and run. |
| A successful invoice write followed by failed refresh looked like a failed write. | Leaving the action retryable could cause a second mutation after the first had already succeeded. | Close the completed action and report that the save succeeded but the list needs Refresh. Test confirms one approval POST with the original version/note payload. |
| Hub navigation left Vite when the public community flag was enabled. | The dashboard hub could hand the user to Next's public hub rather than the requested dashboard workspace. | Remove that automatic handoff from the dashboard section; keep the existing scoped hub APIs. This is an intentional navigation correction requested in this chat and differs from main's former redirect. |
| Shell logo behavior relied on old markup recognition. | A new logo's alt text/dashboard button bypassed the public-route bridge behavior. | Earlier branch work replaced this with explicit public-home links; verify both viewport sizes. |
| Composer preview URLs were allocated during render. | Render retries/StrictMode could leak object URLs or leave lifecycle ownership unclear. | Create/revoke previews in an effect; test failed-send retention and removal cleanup. |
| Chat pagination restoration could run before the request finished. | A loading render could consume the scroll snapshot or cause another page request. | Restore the height delta after the new messages arrive/loading settles; test one request and preserved anchor. |
| Large components mixed unrelated responsibilities; identical filter UI existed in two apps. | Small edits required reasoning about fetching, actions, navigation and presentation in the same file; duplicate UI could drift. | Extract feature-owned responsibilities, share identical filters, keep generic UI ownership explicit and enforce orchestration size limits. |

The sparse candidate dialog is the shared Candidate review component used for platform Interested candidates. Student profiles do not receive fabricated pharmacist registration or rate data. Fields render only when the corresponding profile data exists. A separate backend distinction remains: non-PLATFORM interest serialization returns a minimal identity/bio, whereas revealed PLATFORM interests return the work profile. That policy requires the later intent-versus-drift discussion rather than an unreviewed privacy change.

Priorities for the next decision are: first the preserved backend eligibility/finance/profile-visibility policies (merge blocking until intent is settled); then seeded account/navigation acceptance and the remaining release gates; then bounded maintainability/performance work. The reproduced candidate, invoice, chat, hub/logo and accessibility regressions listed above are fixed locally rather than left as proposals.

Literal/regex extraction is a review aid, not proof of payload or authorization equivalence. Generated route targets, shared-core services and callbacks are traced separately.

## Engineering judgment

The branch has real component reuse and sensible domain boundaries, but also mixed data shapes, large orchestration files, duplicated app presentation and insufficient behavior coverage for the redesign. Those are concrete maintainability/regression risks; source code cannot establish whether AI authored them. The fixes and tests in this pass improve the architecture without a visual rewrite. Merge readiness depends on the recorded contract results and the outstanding policy/release decisions, not an “AI spaghetti” label.
