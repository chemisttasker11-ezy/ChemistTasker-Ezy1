**Audit-only / no staging or production data. Frozen main:** `b77e9fd296bc2710350ef6f3cd402ce2529ffc06`. **S3 status: PENDING** until exact-targeted run is inspected.

`POST /api/v1/ethical/listings/{uuid}/requests/` in `backend/ethical_marketplace/views.py:365-410` loads a `PUBLISHED` listing and validates visibility, destination professional permissions and idempotency key *outside* `transaction.atomic`. The transaction creates an `EthicalTransfer`, locks selected `EthicalStockLot` rows, reserves different lot allocations and writes listing.status=`RESERVED`; it does **not** lock/recheck the single listing's published state. `ethical_marketplace/models.py:164-276` has no one-active-transfer-per-listing unique constraint; individual lot quantities are checked correctly under row lock. For disjoint lots, two transactions may both succeed even though later sequential requests are denied.

**Test construction:** use verified synthetic owners, two real verified pharmacy premises, approved S4 product, reviewed buyer ethical professional permissions and policy, source stock with two distinct available lots, and authentic HTTP requests. Test one sequential reservation first (201) and later second denial. In the negative test use actual **PostgreSQL 16, Django TransactionTestCase, two threads/two database connections, separate UUID request receipts**, a barrier only in the listing visibility call after both read `PUBLISHED`, then let real view/atomic transactions execute unmodified. Assert exactly one 201, one active transfer, one active reservation. If permission/fixture setup fails, treat TEST_INVALID and correct it; do not claim concurrency reproduction.

**Evidence limits:** even two valid reservations would prove an exclusive-listing state transition weakness for two disjoint lots, not actual completed S4 stock transfer, PBS/medical risk, or live pharmacy authorization. The barrier only makes a valid overlap deterministic and does not remove production locks. `.github/workflows/pr200_targeted_postgres_ethics.yml` executes this *targeted* PostgreSQL workflow; no generic full suite, no production migrations, no provider calls.
