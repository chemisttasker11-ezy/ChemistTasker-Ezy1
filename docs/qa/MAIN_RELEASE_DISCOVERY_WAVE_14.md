## B66 — P1 money-calculation candidate: overnight assignment produces negative cancellation wage and falsely skips penalty

**Endpoint → permissions → wage computation → checkout/client.** Authenticated `POST /api/v1/billing/charge-penalty/{shift_id}/` delegates to `user_can_pay_shift_charge_for_pharmacy` to protect tenant/payer scope ([urls.py lines 6–15](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/urls.py#L6-L15), [utils.py lines 58–104](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/utils.py#L58-L104)). The handler iterates all `ShiftSlotAssignment` rows and computes `start_dt` and `end_dt` from **the same** `slot_date`, then uses signed `hours=(end-start)` and `unit_rate`; `total_wage <= 0` returns a successful no-penalty response before reaching Stripe ([views.py lines 699–752](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L699-L752)). But overnight slots are valid: `ShiftSlot.clean` expressly adds a day for end-before-start when validating planned breaks ([models.py lines 348–422](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/models.py#L348-L422)); the canonical shift pricing parser likewise advances end by one day ([pricing.py lines 65–94](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/pricing.py#L65-L94)). **Example:** assigned 22:00–06:00 at $65/hour is +8 worked hours by shift pricing, but −16 hours and −$1040 here, so a real close-to-start cancellation can be represented as zero penalty. This is arithmetic reasoning, not a reproduced Stripe charge.

**Negative:** create paid, future overnight 22:00–06:00 confirmed assignment, choose request time 6h pre-start (freeze clock), mock `stripe.checkout.Session.create`; assert non-zero 8h wage basis and the correct configured percentage, without accidentally applying a missing penalty. Verify one day-shift control at same rate and relevant pharmacy timezone/DST transitions. **Positive:** no assignments or genuinely zero-rate payroll-only terms follow explicit no-penalty policy; owner/Org Admin/roster payer allowed, unrelated users 403. Existing [tests.py lines 283–326](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/tests.py#L283-L326) checks payer authority with **no assignments**, not overnight arithmetic. **Priority:** P1 prospective money leakage. Distinct from B14 (award tables) and B15 (webhook type).

The supported decline transition explicitly permits only PENDING offers and notifies the owner ([offers.py lines 610–661](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/offers.py#L610-L661)). The canonical shared client exposes `declineShiftOffer` but no explicit generic delete action ([api.ts lines 87–111](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/shared-core/src/domains/shifts/api.ts#L87-L111)), so direct authenticated API invocation is the relevant negative path, not a claimed normal UI button.

## B68 — P1 conditional accounting/entitlement candidate: unrelated Stripe subscription invoice can activate local customer entitlement

**Signed provider → fallback → local subscription.** `invoice.paid` first matches `stripe_subscription_id`/add-on ID; if **both fail**, it falls back to **customer ID only** and immediately sets `sub.status='active'` and `current_period_end` from invoice period, without requiring the paid `sub_id` to match a tracked subscription ([views.py lines 885–924](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L885-L924)). `_get_subscription_from_customer` is a simple customer equality lookup ([views.py lines 214–233](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L214-L233)). This is a real policy gap if the same Stripe customer has any independently billed/migrated/canceled subscription: a signed `invoice.paid` for that *different* subscription could mark local ChemistTasker base entitlement active, even if its own base is inactive. The webhook **does validate Stripe signatures** and deduplicates event IDs ([views.py lines 950–1014](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L950-L1014)); this is **not** an arbitrary spoofed webhook or a direct cross-customer authorization bypass. Distinct from B53's **out-of-order events for tracked base vs add-on**: here the `subscription` ID is **not locally recognized at all**.

**Negative:** existing local account customer `cus_A`, tracked base `sub_A` inactive; deliver correctly signed or mocked verified `invoice.paid` with `customer=cus_A` but foreign `subscription=sub_untracked`; local base must stay inactive and expiry unchanged. Also test matching add-on, matching base, empty subscription, second organization customer, duplicated ID. **Positive:** legitimate tracked base invoice reactivates on payment after authenticated provider receipt. Existing [tests.py lines 22–129](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/tests.py#L22-L129) tests webhook dedup/retry, not customer fallback. **Caveat:** legacy migration reconciliation could intentionally permit customer-only matching, but it needs provider-side verified product/subscription details and explicit policy.

## B69 — P1 conditional duplicate-charge candidate: cancellation penalty has no durable cancellation obligation or paid-once guard

The same permitted `charge-penalty/{shift_id}` POST calculates a charge and creates a **new** Stripe Checkout Session on every valid invocation ([views.py lines 699–804](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L699-L804)). There is no cancellation-event ID, settlement nonce, persisted `penalty_pending`, previous settled-payment check, or Stripe idempotency key in this route. Each distinct paid `checkout.session.completed` has its own event ID, and the webhook records a fresh `ShiftPayment` without unique `stripe_payment_intent_id` or shift/type obligation constraint ([views.py lines 836–880](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/views.py#L836-L880), [models.py lines 66–101](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/models.py#L66-L101)). This leaves repeated penalty collection possible for a single cancellation event should a payer finish multiple checkouts. **Not the same as** B04 (empty/duplicate *fulfillment* sessions) or B57 (refund provider reversal).

**Negative:** for a verified single canceled booking with non-zero penalty, submit two requests in short succession, complete both distinct sessions, assert only one charge may settle on that cancellation obligation and duplicate is rejected/reconciled/refunded; event replays alone do not constitute the second session. Test two genuinely different authorized cancellations of the same multi-slot shift if supported (do not block lawful second obligation). **Positive:** one payer authorized to pay one penalty is charged once with immutable invoice and typed payment state. **Caveat:** a cancellation event model/policy may be missing from frozen main; do not assume this endpoint itself cancels an assignment. Existing [tests.py lines 283–305](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/billing/tests.py#L283-L305) only covers role checks with no assignments.

Stripe can maintain both independently billed subscriptions while the DB retains just one. ## B71 — P1 user-flow reliability candidate: shift offer acceptance commits before notification errors can surface to the caller

`ShiftOfferViewSet.accept` changes accepted terms, optionally creates assignments, updates offer/shift status inside `transaction.atomic`, then exits transaction and synchronously calls `notify_shift_users` for worker and owner, and queues email via `async_task`, before returning HTTP 200 ([offers.py lines 370–527](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/offers.py#L370-L527)). `notify_shift_users` invokes `notifications.services.notify_users` ([notifications.py lines 58–94](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/notifications.py#L58-L94)), which creates DB notifications and sends WebSocket/push synchronously ([services.py lines 64–96](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/notifications/services.py#L64-L96)); `async_task` also performs task registration/dispatch and may raise ([task_queue.py lines 33–104](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/core/task_queue.py#L33-L104)). If any synchronous post-commit notification or task dispatch raises, the worker receives an HTTP error **after booking was committed**; retry reaches `Offer is not pending` rather than recovering an idempotent success. This is a **conditional delivery-failure gap**, not a claim that push provider rejection alone raises (push helper catches requests exceptions). Distinct from B54 simultaneous competing offers.

**Negative:** patch `notify_shift_users` or `async_task` to raise after the successful paid/free transaction, POST accept, assert booking and notification recovery state are consistent and worker gets a stable recoverable response, or deferred delivery is explicitly retried without duplicating acceptance. Verify expected state on retry and manager notice without duplicate finalization. **Positive:** normal accept with notifications still works, and a temporary push service outage does not undo a valid reservation. Existing [test_shift_actions_contract.py lines 275–341](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/shifts/test_shift_actions_contract.py#L275-L341) covers offer creation but not post-commit accept notification faults; normal Stripe payment is a separate gate. No runtime fault injection performed.
