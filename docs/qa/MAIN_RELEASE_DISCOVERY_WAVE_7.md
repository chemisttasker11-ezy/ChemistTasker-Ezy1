# PR #200 — Deep senior source tracing, discovery wave 7 (B46–B48)

**Frozen source:** `b77e9fd296bc2710350ef6f3cd402ce2529ffc06` (remote main). **Audit-only**. Existing B01–B45 are not being reopened. These are **new independently traced security/role/data-boundary findings**, not executed exploits. No app changes.

## B46 — P0/P1 candidate: Pending/left pharmacy memberships can access or author private pharmacy, group and organisation Hub content

**Failure mode:** One authenticated user has a `Membership` attached to a pharmacy with `is_active=True` but `status=PENDING`, `REJECTED` or `LEFT`. The private Hub resolver treats that record as authorization for reading/writing confidential pharmacy posts and (if group membership exists) group posts. This is distinct from B41, which concerns shift feeds and notices.

**Complete source chain:**
1. [backend/memberships/models.py#L43-L109](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/memberships/models.py#L43-L109): Membership's status and `is_active` are independent fields, with multiple non-accepted statuses; no DB check constraint tying them together.
2. [backend/pharmacy_hub/access.py#L176-L220](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/access.py#L176-L220): `HubScopeResolver.pharmacy_scope` requires `is_active=True` and staff employment type, not `Membership.Status.ACCEPTED`; `organization_scope` [backend/pharmacy_hub/access.py#L281-L322](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/access.py#L281-L322) repeats the condition and allows organisation Hub reads.
3. [backend/pharmacy_hub/access.py#L81-L130](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/access.py#L81-L130): `get_user_pharmacy_permissions` grants `can_create_post=True` for any active staff membership without checking acceptance.
4. [backend/pharmacy_hub/posts.py#L75-L100](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/posts.py#L75-L100) and [backend/pharmacy_hub/posts.py#L170-L253](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/posts.py#L170-L253): post ViewSet `IsAuthenticated`; list and create resolve scope and return confidential posts or save a new post based on that authorization.
5. [backend/pharmacy_hub/directory.py#L40-L79](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/directory.py#L40-L79) is a strong counterexample: private Hub member directory requires **both active and ACCEPTED**, indicating inconsistent handling of eligibility. Existing [backend/pharmacy_hub/test_api.py#L40-L120](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/test_api.py#L40-L120) checks unauthenticated/outsider and locum-denial, but not active-unaccepted staff.

**Caveat:** Ordinary invitations in [backend/memberships/invites.py#L111-L175](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/memberships/invites.py#L111-L175) usually set PENDING to inactive, so this condition may require pre-existing data, generic membership updates or a stale state. It is not proven reachable merely by a freshly invited pending user. Source currently lacks defense at the Hub boundary.

**Negative and positive tests:** Fixture with ACTIVE+PENDING, ACTIVE+LEFT and ACTIVE+REJECTED FULL_TIME staff record in pharmacy A (also 2nd pharmacy and 2nd organisation). Assert GET `/api/v1/hub/posts/?scope=pharmacy&pharmacy_id=A`, GET private post by id and POST private post are all refused; same for org/group. Assert ACTIVE+ACCEPTED staff and owner/qualified admin retain expected access. Test member directory agrees.

**Status:** Conditional source-level authorization bug candidate; not a runtime-reproduced unauthorized view/write.

## B47 — P1 candidate / owner role-policy decision: Organization email invitations immediately activate full administrative membership for an existing user

**Failure mode:** An organisation user invites an existing registered person into an elevated organisation role. The invite mutation gives that person organisation role and pharmacy scope *before they open/accept the invite email*. The invited user can be unaware of newly granted data access, and the invite could trigger unsolicited privileged access on their currently authenticated account. Whether no-acceptance invitation is allowed is an owner policy decision.

**Complete source chain:**
1. [backend/users/api_organizations.py#L64-L158](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/users/api_organizations.py#L64-L158): `InviteOrgUserView.perform_create` checks inviter delegation but immediately `get_or_create`s an `OrganizationMembership`, sets `role/admin_level/region`, saves and sets pharmacies; only afterwards builds and sends email with password-reset token.
2. [backend/users/models.py#L95-L141](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/users/models.py#L95-L141): `OrganizationMembership` has no pending/accepted/rejected state, and membership is unique by user/organisation.
3. [backend/users/permissions.py#L7-L41](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/users/permissions.py#L7-L41): `OrganizationRolePermission` grants based solely on this membership's role; [backend/dashboards/views.py#L543-L565](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/dashboards/views.py#L543-L565) organisation dashboard reads membership immediately; [backend/users/sessions.py#L58-L75](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/users/sessions.py#L58-L75) returns organisation membership in current-user payload.
4. Contrast [backend/client_profile/test_admin_invitations.py#L26-L71](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/client_profile/test_admin_invitations.py#L26-L71), where pharmacy-admin invitations are explicitly inactive until `accept-invitation`. [backend/users/test_region_delegation.py#L34-L66](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/users/test_region_delegation.py#L34-L66) currently **expects immediate** organization membership after invite: this is a current intentional implementation/contract, not an accidental code regression, hence a **policy-sensitive production gap rather than automatically a P0 bug**.

**Status:** DIRECT source behavior, unresolved product permission policy; no claim of unintended escalation without the acceptance requirement.

## B48 — P1 candidate: Pharmacy Hub mention validation can deliver confidential private post text to ineligible locum or non-accepted members

**Failure mode:** A Hub author controls `tagged_member_ids` in the post creation/edit API. The serializer validates only active membership and pharmacy/group/org membership context. It does not check `status=ACCEPTED` or employment type. An active LOCUM/SHIFT_HERO member may not have any access to the private Hub under `HubScopeResolver.pharmacy_scope`, yet an author can reference their membership ID and the notification path sends the private post's body preview through notifications and email.

**Complete source chain:**
1. [backend/pharmacy_hub/serialization/posts.py#L251-L307](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/serialization/posts.py#L251-L307): `_resolve_tagged_memberships` filters `id__in=..., is_active=True` only and permits same-pharmacy targets; no `status=ACCEPTED` or staff employment-type filter.
2. [backend/pharmacy_hub/posts.py#L91-L166](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/posts.py#L91-L166): `_notify_tagged_members` builds a body excerpt and sends it via `notify_users`, then generates email with `post_body`; trigger from [backend/pharmacy_hub/posts.py#L212-L254](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/posts.py#L212-L254) on valid post creation.
3. [backend/pharmacy_hub/access.py#L170-L206](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/access.py#L170-L206): locum/shift hero without staff membership cannot read private pharmacy Hub; [backend/pharmacy_hub/directory.py#L39-L65](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/pharmacy_hub/directory.py#L39-L65) only returns accepted pharmacy staff, so the picker hides these members but backend accepts forged IDs.
4. [backend/notifications/services.py#L51-L92](https://github.com/chemisttasker11-ezy/ChemistTasker-Ezy1/blob/b77e9fd296bc2710350ef6f3cd402ce2529ffc06/backend/notifications/services.py#L51-L92) emits database notifications, WebSocket and Expo push to account, independently of target's private Hub entitlement.

**Negative and positive tests:** Create a private pharmacy post as accepted staff, include `tagged_member_ids` for (a) active accepted LOCUM, (b) active PENDING FULL_TIME, (c) active LEFT, and (d) accepted FULL_TIME in a foreign pharmacy. Expect 400/no private body in notification, email or push; existing eligible accepted staff in same scope should work. Include browser and Expo app notification previews. Ensure validation happens *before* post persistence or dispatch. This does **not** duplicate B46: the data leak occurs through notification delivery even when the recipient's direct Hub GET is denied.

**Status:** SOURCE-CONFIRMED mismatch with intended eligibility; live request and outbound-notification behavior not yet reproduced.
