### GM01-Q01 — How long should a sign-in last, and should "Keep me signed in" exist on mobile too?

**Plain English:** today a web sign-in lasts a different length depending on a checkbox, and the phone app never asks — it always stays signed in. The odd part: ticking "keep me signed in" on the web actually gives you a *shorter* refresh token (7 days) than not ticking it (90 days). The owner needs to choose one clear rule for how long each sign-in lasts on each device.

**ACTUAL TODAY — Web:** login screen has "Keep me signed in", default off (`frontend_web/src/pages/login.tsx`, `rememberMe = useState(false)`). Backend (`backend/users/sessions.py` `_set_auth_cookies`): `persistent = remember_me is not False`, so ticked → cookies persist; unticked → session cookie (browser close ends it). Refresh lifetime (`backend/users/serializers.py`): `remember_me is True` → 7 days (`JWT_REMEMBER_ME_REFRESH_TOKEN_LIFETIME`); `remember_me is False` → session cookie but the token itself still carries the 90-day lifetime; `remember_me` not sent at all → persistent + 90 days. Access token 30 min everywhere. **ACTUAL TODAY — Expo:** no checkbox anywhere; `loginWithCredentials` sends no `remember_me` (`frontend_mobile/utils/nativeIdentityTransport.ts`), so the backend treats it as persistent + 90-day refresh, and tokens live in SecureStore indefinitely until logout/refresh failure (`frontend_mobile/utils/authSession.ts`). **Parity gap:** web defaults to "forget me when the browser closes", mobile defaults to "remember me for 90 days" — opposite defaults, never chosen by the owner.
**Normal case:** worker signs in daily on a shared pharmacy computer vs their own phone. **Edge case:** refresh token stolen — 90 days of access vs 7. **Retry/concurrency:** refresh rotation blacklists only the rotated token; a stolen refresh can be used until expiry. **Denied role:** none. **Payment/notification:** none directly; a stale session can still receive push until logout deletes the device token.
**RECOMMENDED:** Keep the web checkbox, fix the inversion (ticked = 90 days, unticked = session cookie + short refresh, e.g. 24 h), and add the same choice on Expo (default off for shared devices, on for personal phones). Severity: medium — security + convenience. Benefit: one predictable rule, shorter exposure if a token leaks. Risk: workers on shared computers stay signed in if they tick the box.
**ALTERNATIVE A — Keep current logic:** web checkbox as-is (including the 7-day inversion), Expo always persistent. Trade-off: no work, but the inversion stays a trap and the two clients keep opposite defaults.
**ALTERNATIVE B — Short sessions everywhere:** access 30 min, refresh 24 h max on all clients, no remember-me. Trade-off: safest, but locums sign in several times a day; biometric on Expo softens it.
**ALTERNATIVE C — Long sessions everywhere:** 90-day refresh on web and Expo, no checkbox. Trade-off: most convenient, weakest if a device is lost — needs "sign out everywhere" (GM01-Q06) to be safe.
**Other (describe) / Defer:** owner may defer, but this blocks GM01-Q06/Q07 wording.

### GM01-Q08 — When a session expires mid-use, what should the worker see?

**Plain English:** today there is no single "your session expired, sign in again" moment. Each screen fails on its own; the web app quietly clears your session when you click back into the tab, and the phone app clears it when it restarts. A worker can be mid-form when their session dies.
