## 1. Traced flow — ACTUAL TODAY

### 1.1 What exists (one paragraph per surface)

**Chat — conversations.** `backend/chat/models.py`: `Conversation` (type GROUP/DM, optional `pharmacy` FK — exactly one community chat per pharmacy via `uniq_community_chat_per_pharmacy`; `dm_key` `"low:high"` user-id pair via `make_dm_key`, unique per pair), `Participant` (membership FK, `is_admin`, `last_read_at`, per-user `is_pinned` + per-user `pinned_message`), `Message` (sender = Membership, `body`, `attachment` FileField, `is_deleted`/`is_edited`/`original_body`), `MessageReaction` (exactly 4 emoji: 👍 ❤️ 🔥 💩; one reaction per user per message, toggle/change supported). **There is no `shift` FK on any chat model — no shift-linked thread exists.** There is no Report/Block/Mute model in the chat app at all.

**Chat — who is in a room.** `backend/chat/realtime.py::participant_can_receive_chat_updates` is the single eligibility rule used by REST, WS, and badges: membership must be ACCEPTED and active, user active; pharmacy community GROUP rooms additionally require `membership.pharmacy_id == conversation.pharmacy_id` and a staff employment type (`PHARMACY_STAFF_EMPLOYMENT_TYPES`); favourite locums are *explicitly excluded* from community chats even if a legacy Participant row exists. The one exception: DM-only inactive `CONTACT` memberships (see Q01) stay eligible for DMs. `accessible_conversations_queryset` is the matching REST visibility rule. Revocation is enforced per-message/per-event (PR201; `docs/qa/PR201_PHASE6_CHAT_REVOCATION_20261026.md`, `docs/qa/PR201_PHASE6_CHAT_SUBRESOURCE_SECURITY_20261026.md`).

**Chat — community chat auto-creation.** `backend/chat/signals.py::sync_membership_to_community_chat`: on Membership save, an accepted + active staff member auto-creates (or joins) the one GROUP conversation for their pharmacy and becomes a Participant; if the membership stops qualifying, its Participant rows for that pharmacy's GROUP chats are deleted. So staff never "join" a pharmacy chat — membership *is* the join.

**Chat — DMs.** `backend/chat/views.py::ConversationViewSet._get_or_create_dm_conversation` (via `POST /rooms/get-or-create-dm-by-user/` with `partner_user_id`, or legacy `POST /rooms/get-or-create-dm/` with `partner_membership_id`): the sender needs *any* active membership; the partner needs none — if they have no active membership, the backend **creates an inactive CONTACT membership for them under the sender's pharmacy** (`role='STUDENT'`, `employment_type='CONTACT'`, `is_active=False`, `invited_by=sender`). No check that the two users share a pharmacy, a shift, an offer, or any relationship. No Verified/AHPRA check on the REST path. Self-DM is 400; missing partner is 404; no active sender membership is 403. Legacy DMs without a `dm_key` are found by participant pair and backfilled.

**Chat — shift contacts (the only shift link).** `GET /rooms/shift-contacts/` (`ConversationViewSet.shift_contacts`): for a manager it returns workers with `ShiftSlotAssignment`s at their pharmacies with `slot_date >= today`; for a worker it returns the pharmacy owner, org admins, and pharmacy admins for their upcoming assignments. It is a *people list only* — tapping a contact just opens a generic DM (`startDirectChat` → `get-or-create-dm-by-user`). Past shifts disappear from the list; offers/interest (not yet assignments) never appear; there is no shift context inside the thread.

**Chat — sending.** Two writers, same table. REST: `POST /rooms/{id}/messages/` (body and/or attachments; empty = 400) and `POST /messages/` (`MessageViewSet.create`). WS: `ws/chat/rooms/{room_id}/` (`backend/chat/routing.py`, `RoomConsumer`), `{"type":"message"}` → `sanitize_chat_text` (strips script/style + HTML tags, collapses whitespace — **no profanity/abuse filter**) → `Message.objects.create` inside a transaction with a `select_for_update()` membership lock (revocation racing the send loses and the socket is closed 4403). Both writers broadcast `message.created` over the channel layer; the `post_save` signal (`signals.py::broadcast_new_message`, `transaction.on_commit`) *also* broadcasts and sends the notification — so a REST send emits the room event twice (clients dedupe by message id; see C06) but the push/badge path runs once from the signal. WS connect requires: authenticated, not anonymous (4401), AHPRA-not-frozen (4403, re-checked every 10 s and on every send/delivery), and a currently-eligible Participant (4403). Typing is broadcast with a 1 s server cooldown. Messages are paginated 50/page, max 100 (`ChatMessagePagination`).

**Chat — attachments.** `POST` with `attachment` files: validated by `infrastructure/file_validation.py::validate_uploaded_file` against `ATTACHMENT_UPLOAD_POLICY` — pdf/docx/jpg/jpeg/png/webp/gif only, 15 MB max, content sniffed (a disguised file is rejected and nothing is stored). A batch is validated *before* any message is saved, so one bad file rejects the whole batch with no side effects (`backend/chat/test_api.py::test_invalid_attachment_anywhere_rejects_batch_without_side_effects`; `docs/qa/CHAT_ATTACHMENT_BATCH_VALIDATION_20261029.md`). The first message carries the caption; each further file becomes its own message with empty body. Files are served only through `GET /messages/{id}/attachment/` to a currently-authorised participant (`MessageViewSet.attachment`: `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`; images inline, others download). No raw storage URL is ever exposed. **No virus-scan step was found** in the validation path (unknown — verify with infra; see backlog).

**Chat — edit / delete / react / pin / read.** Edit (`PATCH /messages/{id}/`): sender only; empty body rejected; first edit stores `original_body`, sets `is_edited`. Delete (`DELETE /messages/{id}/`): sender only, soft delete — body/attachment/original_body cleared, `is_deleted=True`, the stored file is deleted on commit; other participants see an empty tombstone. React (`POST /messages/{id}/react/`): participant only, one of the 4 emoji; same emoji again removes it, a different one replaces it. Pin (`POST /rooms/{id}/toggle-pin/`): per-user conversation pin and per-user message pin. Read (`POST /rooms/{id}/read/`): sets `last_read_at=now`, broadcasts `message.read` + updated badge. Unread counts exclude the reader's own messages and count messages after `last_read_at`. Delete conversation (`DELETE /rooms/{id}/`): community chat — comms-admin capability only (`organizations.access.CAPABILITY_MANAGE_COMMS`); custom group — effectively creator-only (see C05); DM — delete-for-me only (own Participant row removed; conversation deleted only when no participants remain). **There is no message search, no mute, no block, no report in chat.**

**Chat — notifications.** Every new message (signal, on commit): per-recipient WS badge (`realtime.py::broadcast_message_badge`, `message.badge` with unread count + 160-char body preview + sender name) and a `Notification` row of `Type.MESSAGE` via `notifications.services.notify_users` with a role-based web action URL (`signals.py::CHAT_ROUTE_BY_ROLE`: `/dashboard/{owner,pharmacist,otherstaff,organization,explorer}/chat?conversationId=…`; default owner). Push: `notify_users` → `_send_expo_push` (Expo push API) when `push_allowed_for_notification` passes — `MESSAGE` maps to the `push_messages` preference (`notifications/services.py:126`). A channel-layer outage does **not** skip the durable notification/push (`test_api.py::test_channel_outage_does_not_skip_durable_chat_notification_and_push`). Email delivery of chat notifications was **not verified** in this trace (unknown). There is no per-room mute and no verified quiet-hours rule.

**Chat — history & retention.** Messages are kept indefinitely. No retention/expiry/cleanup job for chat was found (no chat entry in `backend/core/celery.py`; no management command). Soft-deleted messages keep their row. Hard-deleting a GROUP conversation cascades to all its messages. Revoked staff lose access but their messages stay visible to remaining participants (`test_api.py::test_removing_staff_keeps_their_messages_visible_to_other_participants`). Identity of a former member is preserved via `ChatParticipantView` (`GET /chat-participants/` lists memberships sharing the requester's rooms, including inactive ones, "to ensure their names are preserved in the chat history").

**Pharmacy Hub — scopes.** `backend/pharmacy_hub/access.py::HubScopeResolver`: four scope types. *Pharmacy*: accepted active staff membership at that pharmacy, or the pharmacy owner, or an org member with MANAGE_COMMS covering it; admin = owner/org-admin/pharmacy-admin. *Organisation*: org membership with comms capability. *Community group*: `PharmacyCommunityGroup` (+ `PharmacyCommunityGroupMembership`, admin flag). *Platform*: OTP-verified (`is_otp_verified`, `users/models.py:80`, default False) + the role's own hub only (`get_user_chemisttasker_hubs`: everyone gets `public`; OWNER→owner, PHARMACIST→pharmacist, EXPLORER→explorer, OTHER_STAFF intern→intern else staff). Posting requires an author membership (`ensure_author_membership`, which can activate/create one in some scopes — not fully traced, mark as partially inspected). **No onboarding-Verified (email+mobile+AHPRA) check exists anywhere in the hub path.**

**Pharmacy Hub — posts/comments/polls.** `backend/pharmacy_hub/models.py`: `PharmacyHubPost` (pharmacy/org/community_group/platform_hub, `visibility`, `allow_comments`, pin + `pinned_at`/`pinned_by`, `tagged_members` M2M, `comment_count`, `reaction_summary` JSON, edit history `original_body`/`is_edited`/`last_edited_at`/`last_edited_by`, soft delete `deleted_at`), `PharmacyHubComment` (one-level `parent_comment`, same edit/soft-delete pattern), `PharmacyHubReaction` / `PharmacyHubCommentReaction` / `PharmacyHubPollReaction` (`HubReactionType` — values not listed here, inspect `models.py:417`), `PharmacyHubAttachment` (kind IMAGE/GIF/FILE, same 15 MB `ATTACHMENT_UPLOAD_POLICY` via `scoping.py::HubAttachmentMixin`), `PharmacyHubPoll` (+ options/votes/comments, `closes_at`/`is_closed`). Write API `backend/pharmacy_hub/urls.py` (`/hub/posts/`, `/hub/posts/{id}/pin|unpin`, `/hub/posts/{id}/comments/`, `/hub/polls/`, `/hub/polls/{id}/vote/`, `/hub/groups/`, `/hub/members/`, `/hub/context/`, `/hub/pharmacies/{id}/profile/`, `/hub/organizations/{id}/profile/`). Tagging a member sends an in-app notification *and* an email (`posts.py::_notify_tagged_members`, templates `backend/templates/emails/hub_post_tagged.html/.txt`); commenting/reacting notifies the post author (`pharmacy_hub/notifications.py::_notify_hub_post_owner`, type `alert`, action URL `/dashboard/pharmacy-hub?…`). Public (anonymous) reads of platform-hub posts go through `public_hub/community.py` (`/api/hub/community/`, `…/posts/`, `…/polls/`, `…/posts/{id}/comments|report`, `…/attachments/{id}/`, `…/boards/{kind}/{id}/report/`), gated by `PUBLIC_COMMUNITY_ENABLED` (see below); authors are shown by full name only (`public_name`: never email/username/role).

**Public Hub — articles.** `backend/public_hub/models.py`: `Article` (blog/news × 5 topics, draft/published/archived, `published_at` required to publish, slug permanent after publishing, cover-alt required for accessibility, source name+URL paired), `Comment` (3,000 chars, one-level replies, `hidden`/`deleted`), `Reaction` (like/insightful/support; one per user per article/comment), `Report` (one per user per comment, `resolved` flag), `BoardReport` (talent-post / job-board-shift reports, "reviewed in the Moderation tab (board:* areas)"), plus the editorial workflow (`ContentDocument`/`ContentRevision` with draft→submitted→scheduled→published, writer/publisher assignments per area, `ContentAdministrator`, `ContentAudit`, `ContentInvitation`). Reads are `AllowAny`; writes need `VerifiedMember` (`public_hub/permissions.py::verified` = authenticated + active + `is_otp_verified`, defaulting to True if the attribute is missing — in practice the field exists with default False, so unverified users are blocked; the default-True fallback is fragile, see C11). Writes are throttled at 30/minute (`DiscussionThrottle`). **The whole public surface 404s unless `PUBLIC_COMMUNITY_ENABLED` is on — it defaults to `DEBUG` (`backend/core/settings.py:724`) — i.e. off in production unless the env flag is set.** The moderation queue UI itself was not traced (unknown whether a staff member can actually see and resolve reports outside Django admin).

### GM20-Q01 — Who can start a direct chat with whom? [FIRST QUESTION — see §3]
- **Context:** There is no rule today linking a DM to any working relationship. A DM is also the moment a stranger learns the other person's full name, email and photo (see Q08), and it is the only way a worker can ask a question before accepting work (see TB-Q07).
- **ACTUAL TODAY:** Any signed-in user with any active membership can open a DM with any user id (`POST /rooms/get-or-create-dm-by-user/`, `backend/chat/views.py::ConversationViewSet._get_or_create_dm_conversation`). No shared pharmacy, shift, offer, favourite or verification check. If the other person has no active membership, the backend silently creates an inactive CONTACT membership for them under the *sender's* pharmacy (`role='STUDENT'`, `employment_type='CONTACT'`). No Verified/AHPRA check on the REST path. Web's picker and Expo's picker narrow who you *find*, but the API does not enforce it. Normal case: owner DMs a locum — works. Edge case: a stranger DMs any worker whose user id they know/guess; an Explorer with no pharmacy link can be pulled into a CONTACT membership under a pharmacy they never joined. Retry/concurrency: `dm_key` + transaction dedupes, so two simultaneous creates return the same room. Denied role/wrong tenant: none — there is no tenant check on DMs. Payment/notification side effects: none until the first message, which then notifies + pushes (F19).
- **Type:** decision. **Severity:** Launch-blocking (safety + privacy).
- **Options:**
  - **KEEP — "Keep current logic":** anyone with an active membership can DM anyone, CONTACT auto-created. Simplest; matches "everybody posts from both sides" openness. Trade-off: open to spam, poaching, and unsolicited contact; a worker's email is exposed to any DM partner (Q08).
  - **A — "Shared relationship only":** DM allowed only if the two users share a pharmacy (same membership pharmacy), a favourite link, or an upcoming/past assignment. Strangers get "You don't work together yet — send a shift offer or request booking instead." Trade-off: blocks cold outreach between pharmacies; needs a visible-membership lookup at DM time.
  - **B — "Shift-linked only":** DM allowed only from the shift-contacts list (an upcoming assignment exists) or inside a shift thread (see Q03). Trade-off: cleanest safety story, but no pre-booking questions at all unless combined with an enquiry flow (TB-Q07 option B).
  - **C — "Owners/admins can start, workers can reply":** only OWNER/ORG_ADMIN/pharmacy-admin can initiate; workers can reply to DMs started with them and DM within their own pharmacy team. Trade-off: matches the web/Expo FAB gates, but blocks worker-to-worker chat (e.g. two locums covering the same pharmacy).
  - **Other (describe) / Defer.**
- **RECOMMENDED: A.** Shared-relationship-only keeps the marketplace usable (teammates, favourites, assigned workers can always talk) while closing cold-contact spam and the silent CONTACT-membership side effect. It is the smallest change that makes Q02/Q08 safe. **Why not KEEP:** an open DM to any user id, combined with full identity exposure, is the single biggest safety gap in this area; it will be used for off-platform poaching and harassment in week one. **Why not B:** it kills pre-booking questions entirely and contradicts TB-Q07's enquiry need. **Risks of A:** needs a clear "why can't I message?" error and a path (offer/request booking) so legitimate cold contact still works.
- **Sources:** `backend/chat/views.py::_get_or_create_dm_conversation`, `get_or_create_dm_by_user`, `get_or_create_dm` @ `97c4543`; `backend/chat/models.py::make_dm_key`; `shared-core/src/domains/chat/api.ts::getOrCreateDmByUser/startDm`.

## 3. SINGLE first decision question to ask the owner first

**GM20-Q01 — Who can start a direct chat with whom?**

In plain English: today, anyone who has signed in and has any active role can send a direct message to *any* other user — even a complete stranger, even before any shift, offer, or booking exists — and the other person's full name, email and photo are shown immediately. If the other person has never used the app properly, the system quietly creates a "contact" record for them under the *sender's* pharmacy. There is no check that the two people work together, and no verified-pharmacist check.

**Options:**
- **Keep current logic** — anyone with an active role can DM anyone; a contact record is auto-created for the other person. Simplest, most open; but open to spam, poaching, and unwanted contact, and a worker's email is exposed to any stranger who messages them.
- **A — Shared relationship only (RECOMMENDED)** — you can DM someone only if you share a pharmacy, are favourites, or have (or had) an assignment together. Otherwise the app says "You don't work together yet — send a shift offer or request a booking instead." Keeps teammates, favourites and assigned workers talking; closes cold contact.
- **B — Shift-linked only** — you can DM only from the shift-contacts list (an upcoming assignment exists). Safest, but nobody can ask a question before a booking exists.
- **C — Owners/admins start, workers reply** — only owners, organisation admins and pharmacy admins can start a DM; workers can reply and can DM inside their own pharmacy team. Matches the buttons the apps already show, but blocks worker-to-worker chat.
- **Other (describe) / Defer.**

**Why first:** every other chat decision depends on it — when chat unlocks (Q02), what identity is safe to show (Q08), and whether reporting (Q06) is urgent all change with the answer. It is also the only question whose "keep" option leaves a stranger able to contact any worker and learn their email.
