**Plain-English glossary (used before jargon):** *Owner* = the person who signs up with role OWNER and owns the pharmacy record. *Pharmacy* = one shop/site (name, address, ABN, hours, rates). *ABN* = Australian Business Number, the shop's business ID. *Verified* (pharmacy) = a yes/no flag a platform admin sets; *ABN-verified* = the ABN was looked up on the government ABR register and the owner confirmed the entity name matches. *Chain* = a group of pharmacies owned by one owner. *Organisation* = a larger corporate group that can claim pharmacies. *Setup gate* = the app forcing a new owner to finish their personal profile, then add at least one pharmacy, before reaching the dashboard. *Stripe Checkout* = the payment page that opens fresh for every booking fee. *Saved payment method* = a card stored once and charged automatically later (does not exist today).

## §2 — Traced flow (plain English, actor by actor)

**The owner signs up.** Anyone can self-register as OWNER — no approval, no invitation, no admin check. The same four roles (OWNER, PHARMACIST, OTHER_STAFF, EXPLORER) exist on web. The account exists before any pharmacy exists.

**The gate.** On login, the app asks: does this owner have a finished personal profile, and at least one pharmacy? If not, it sends them to setup instead of the dashboard. On Expo this is a real gate on every screen: leave setup unfinished and any other screen bounces you back. On Vite web the gate fires at login and inside the setup pages themselves; no global route guard was found in `main.tsx`, so a web owner who types a dashboard URL directly may or may not be bounced — that is unverified, and it is a Web/Expo difference to check (CG-08).

**Step 1 — the person.** The owner fills in their own profile: are they a pharmacy manager or a pharmacist, is this a chain pharmacy, and if so how many pharmacies. A pharmacist-owner can add their AHPRA number. They can add a photo and a government ID. Submitting marks the profile "submitted for verification" — but nothing in the code was found that actually verifies the *owner person* at this point, and the gate counts the profile as "complete" on a loose test (submitted flag, or just first/last name + username + phone + role). An owner with no ID and no AHPRA still passes the gate.

**Step 2 — the shop(s).** The owner adds pharmacies, one form per shop, until they reach the number they declared (or just one, if they said "not a chain"). The backend only insists on two things: a name and an 11-digit ABN. The web and Expo forms ask for much more — street address, suburb, postcode, state, opening hours day by day, what software the shop runs, what services it offers, how many scripts a day, what roles it needs, default pay rates — but all of that is optional in the backend. The one extra rule the web form adds is: if you pick "fixed rate", you must fill in all four day rates (weekday, Saturday, Sunday, public holiday). Whether Expo enforces that same rule was not verified.

**The ABN check.** Inside the pharmacy form the owner types the ABN, presses "Check ABN", and the app looks it up on the government ABR register and shows the legal entity name, type, status and GST details. The owner then presses "Confirm this ABN". Only that human confirm — plus the ABR data — makes the pharmacy "ABN-verified". The automatic background re-check never verifies on its own; it only refreshes the ABR data. If the owner later changes the ABN, everything resets to unverified, and once verified-and-confirmed the ABN locks: it cannot be changed at all without an error. If the ABR site is down, the check fails gracefully and the owner simply cannot confirm yet.

**Skipping.** The pharmacy step can be skipped ("Continue later"). The skip is not recorded on the server at all — it lives only on the device. On the web it lives in the tab's session storage, so closing the tab forgets it and the owner is asked again next login. On Expo it lives in persistent phone storage, so skipping once means never being asked again. Either way, an owner can reach the dashboard with zero pharmacies, and nothing reminds them later.

**The mystery flag: `verified`.** Every pharmacy has a `verified` yes/no flag that starts as No. Nobody in the app can set it — it is read-only in the API — and no screen shows it. The only places the code reads it are the two marketplaces (the ordinary goods marketplace and the ethical marketplace), where only verified pharmacies can trade. It does *not* stop a pharmacy posting shifts. Who sets it, on what evidence, and whether the owner is ever told, is unknown from the code inspected. That is the single biggest documentation hole in GM-03 (see GM-03-Q01 and CG-01).

**Posting without verification.** A pharmacy with an unverified ABN and `verified = No` can post shifts to every audience, including the public board, and workers can accept them. The posting code checks daily public-post limits and rate defaults, but never checks either verification flag. This is exactly the situation #184 described in October 2026 — it has not changed.

**Groups: three overlapping ideas.** A multi-pharmacy owner has three different "group" concepts in the code, and they are not the same thing: (1) simply owning several pharmacies; (2) a *Chain* — a named group the owner (or an organisation admin) creates and adds pharmacies to; (3) an *Organisation* — a corporate group, created only by a platform admin, which claims pharmacies through a formal claim (pending → accepted/rejected, one accepted claim per pharmacy) and invites its people by email. PR #249 tightened claims for people in several organisations (an explicit organisation must now be named). Which of these three is "the group" for shift audiences, fees and payroll is not settled anywhere in GM-03's code — that is a decision, GM-03-Q08.

**Organisations cannot join themselves.** There is no self-sign-up for an organisation. A platform admin creates it, then the organisation claims pharmacies. A web "create organisation" page still exists in the code but is not linked from any route, and even if it were, the backend would reject a non-admin with a 403. Unchanged since October 2026.

**Two profiles, one person.** The owner's *personal* profile (manager/pharmacist, AHPRA, ID) and the *pharmacy* profile (ABN, address, hours, rates) are separate records joined by a link. The owner is also automatically made a member and an OWNER-level admin of their own pharmacy, and cannot be removed or demoted from it. But nothing ties "the responsible pharmacist on site today" to the pharmacy record: if the owner's AHPRA is suspended, the owner record flips to Manager while the pharmacy record is untouched and can still post pharmacist shifts.

**Money.** There is no saved card and no payment step anywhere in setup. Every booking fee opens a fresh Stripe Checkout page (card only), $30 per locum shift / $80 per job, halved for subscribers ($15/$40 — the subscriber discount that was broken in October 2026 now works; the price IDs are still hard-coded). A subscription can be started from a card on the owner-profile page, but it is optional and separate. The old 10%/20% cancellation-penalty checkout is still live in the code even though the October audit said to remove it. Billing goes live by a date setting (`2025-06-01`) whose comment says "June 1, 2026" — the date and the comment disagree, and the free-trial setting is 0 days.

**Editing later.** The owner (or an authorised admin) can edit their pharmacy later — address, hours, rates, documents — except the ABN once locked, and except changing which pharmacy a shift belongs to once people have engaged with it. Deleting a pharmacy is blocked if it has shifts. There is no "close / suspend / deactivate pharmacy" switch: a pharmacy is either there or deleted.

**Documents and payroll.** The pharmacy can hold four kinds of documents (methadone/S8 protocols, Queensland SUMP papers, SOPs, induction guides). All are optional, nobody reviews them in-app, and they never expire. The "use ChemistTasker payroll" switch is real in the backend (default off) but appears in *neither* the web nor the Expo pharmacy form — it lives on a separate workforce-settings screen the owner has to find. So an owner can finish setup without ever seeing the payroll choice.

### GM-03-Q01 — What must a pharmacy pass before posting to outside workers?

> **Merged 22 Nov: asked once, as ON-Q11 in GM-02.** Answer it there; this copy stays for its own evidence and is not asked again.
- **Old ID:** ON-Q11 (gap ON-06). **Status: STILL VALID, unchanged. Decision: OPEN.**
- **Question (plain English):** Before a pharmacy can offer shifts to locums it doesn't already know, what proof should it have passed — nothing, a checked ABN, or a checked ABN plus a human admin review?
- **ACTUAL TODAY:** Nothing. `post_shift()` (`backend/shifts/posting.py:62`) checks neither `Pharmacy.verified` nor `abn_verified`. Any pharmacy row — fresh, ABN unchecked, `verified=False` — can post to every tier including public, and workers can accept. The `verified` flag is only read by the two marketplaces (`backend/marketplace/policy.py:99-100`; `backend/ethical_marketplace/policy.py:89,94,127`). Nobody in-app can set `verified` (read-only in `backend/organizations/serializers.py:211`); who sets it, on what evidence, is unknown.
- **RECOMMENDED: D — ABN verified for chain/organisation tiers; ABN verified plus admin-verified before public.** (Same recommendation as #184.) Rationale: chain/org workers already know the site, so an ABN check is proportionate; public workers have no other signal, so a human review is the trust the fee buys. Severity: **Launch-blocking.** Benefits: fake/unverifiable sites cannot reach strangers; workers trust the board; disputes and no-shows from phantom pharmacies fall. Risks: admin review is a bottleneck at launch (someone must do it, and fast); a genuine new pharmacy waits. Legal/financial: an unverified pharmacy that books a worker and then cannot pay, or is not a real business, creates wage and safety exposure the platform is in the middle of.
- **ALTERNATIVE A — Keep current logic:** no checks before any tier. Scenario: a new owner signs up at 9am, posts a public pharmacist shift at 9:05, a locum accepts and drives 40 minutes — the "pharmacy" is a test row with a made-up ABN. Trade-off: fastest onboarding, highest trust risk; the first bad story defines the brand.
- **ALTERNATIVE B — ABN verified for any outside post:** automatic ABN lookup + owner confirm only, no human. Scenario: a real single pharmacy with a valid ABN posts publicly the same day; a shelf company with a valid ABN but no premises also passes. Trade-off: no bottleneck, but ABN ≠ real, staffed, lawful premises.
- **ALTERNATIVE C — ABN plus admin check before *any* outside post (uniform, no tier split):** every post to favourites, chain, org or public waits for ABN verification plus a human admin review. Senior-review correction: C as written in #184 was the same as D's public half; restated here as the genuinely uniform variant so it is distinct from D's tier split. Scenario: a new pharmacy's first post to its own favourites also waits for review — slowest, but one rule everywhere and no tier-boundary disputes. Trade-off: maximum trust, maximum bottleneck; even known locums wait.
- **Other (describe) / Defer:** e.g. "admin check only for the first public post per pharmacy, then ABN-only" — needs a "first-post reviewed" state that does not exist today.
- **Normal case:** owner completes ABN confirm → posts to favourites → later to public after review. **Edge case:** ABR is down on launch day — ABN cannot be confirmed, so under B/D the pharmacy cannot post at all; needs a documented fallback (manual ABN evidence upload? temporary pass?). **Retry/concurrency:** two owners, same ABN — no uniqueness on `Pharmacy.abn` was found; two rows can hold one ABN (UNKNOWN, verify). **Denied role / wrong tenant:** a manager posting for a pharmacy they don't administer is blocked by shift access (not re-traced); the gate itself does not check *who* verified. **Payment/notification side effects:** none today; under D, a review queue needs "approved / rejected + reason" notifications to the owner. **Web/Expo difference:** none — the gate (or lack of it) is backend, identical for both.

- **Question:** The pharmacy has default pay rates (weekday, Saturday, Sunday, public holiday, early morning, late night) and a "use ChemistTasker payroll" switch. Should the owner set them during setup, what are the defaults if they don't, and is payroll on or off unless they choose?
- **ACTUAL TODAY:** Rates are optional in the pharmacy form on both clients; the web form forces all four day rates if FIXED is chosen (Expo: unknown). If no rate is given, a FIXED shift falls back to `default_fixed_rate or weekday_rate or slot rate or $0.00` (`posting.py`). The payroll switch defaults to **off** and is **not in either pharmacy form** — it lives on a separate workforce-settings screen (web `usePayrollSetting.ts`; Expo `app/workforce-settings.tsx`). With payroll off, "roster and attendance still produce timesheets without requiring Award classifications or pay rates" (model help text).
- **RECOMMENDED: Keep payroll off by default; surface the switch in the pharmacy form (setup + edit) on both clients with a one-line explanation of what changes; require at least a weekday rate before the first FIXED-rate post (not before setup completes).** Rationale: payroll off is the safe default (no Award/pay-rate obligations the owner didn't ask for), but a switch the owner never sees is not a choice. Severity: **Medium.** Benefits: owners who want payroll find it; owners who don't aren't forced through Award setup. Risks: surfacing it in setup lengthens the form; a wrong toggle changes timesheet/payroll routing (GM-09). Legal/financial: payroll on means Award classifications and pay rates become required downstream — the owner must understand that before toggling.
- **ALTERNATIVE A — Keep current logic:** rates optional, payroll hidden in workforce settings, off by default. Scenario: an owner posts FIXED shifts with no rates and the shift defaults to $0.00; another owner never finds payroll and pays locums outside the system. Trade-off: zero work, silent misconfiguration.
- **ALTERNATIVE B — Payroll on by default:** every pharmacy gets Award/payroll from day one. Scenario: a small owner who only wants locum cover must complete Award classifications before posting. Trade-off: correct payroll, heavy onboarding.
- **Other (describe) / Defer.**
- **Normal case:** owner sets weekday/Saturday/Sunday/public-holiday rates at setup → new shifts prefill them. **Edge case:** owner sets FIXED with only a weekday rate on Expo (if the web rule is missing there) → other days fall back silently. **Retry/concurrency:** rate sync from a posted shift can overwrite pharmacy defaults (`sync_pharmacy_rate_defaults`) — under the recommendation, that write-back needs the owner's eyes (it happens today without notice). **Denied role:** only pharmacy editors can change rates/payroll. **Payment:** rates drive the agreed wage and therefore the booking fee base; payroll toggle drives timesheet routing. **Notification:** none today. **Web/Expo difference:** the FIXED four-rate rule (web-only, verified) and the payroll screen location (separate on both, but different screens).

## §5 — The SINGLE first decision question to ask the owner first

### GM-03-Q01 — What must a pharmacy pass before posting to outside workers?

Ask this first because everything downstream depends on it: whether a fake or unverifiable shop can reach strangers, whether the `verified` flag means anything, whether an admin review queue must exist before launch, and whether the marketplace decisions can rely on the flag. It is launch-blocking, and every other GM-03 question can be answered after it without rework — but if it is answered late, the posting, marketplace and admin work all have to be revisited.

**Question in plain English:** Before a pharmacy can offer shifts to locums it doesn't already know, what proof should it have passed — nothing, a checked ABN, or a checked ABN plus a human admin review?

**How it works today:** Nothing is checked. Any pharmacy can post to every tier, including the public board, and workers can accept — even with an unchecked ABN and `verified = No`. (`backend/shifts/posting.py:62 post_shift()` checks neither flag.)

**Options:**
- **A — Keep current logic:** No pharmacy checks before posting to any tier. *Fastest onboarding; a fake site can post publicly and be accepted.*
- **B — ABN verified for any outside post:** Automatic ABN lookup + owner confirm only. *No human bottleneck; but a valid ABN is not proof of a real, staffed premises.*
- **C — ABN plus admin check before public:** A person reviews the site before public posting (chain/org tiers need ABN only — this is the tier split in D; if the owner prefers no split, C is the uniform version).
- **D — B for chain/org, C for public (RECOMMENDED):** ABN verified for chain and organisation tiers; ABN verified plus admin-verified before the public tier. *Chain/org workers already know the site; public workers have no other signal, so a human review is the trust the fee buys. (Locumate activates pharmacy accounts only after review — #184 source.)*
- **Other (describe):** e.g. "admin check only for the first public post per pharmacy, then ABN-only."
- **Defer:** explicitly deferring means launching with option A by default — say so, don't leave it implicit.

**Recommendation:** D. **Severity:** launch-blocking. **Decision status:** OPEN — NOT DECIDED.
